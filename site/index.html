Eight layers

One delegation walks through all eight. Each: what ccx does, one measured number, one limit (Measured). Every command and option, including ccx ask, ccx send, ccx batch, ccx agents, --review and probable verdicts: features. A sub-agent cannot delegate again through ccx; config changes are shown as a dry run first, with a backup.

① Conversation

ccx discuss gets two or three vendors' views; the board (ccx say, ccx reply) lets open sessions write to each other. Not measured yet; a Claude Code lead sees a message only on its next turn.

② Shared memory

Your hub and the project's .ccx/; the notes a task is about go into every brief; ccx handoff passes the baton. A project note was followed 9/9 vs 0/9; 3 tasks × 3.

③ Splitting and pipeline

ccx q: a durable queue, one worktree per piece, merged by dependency. Handing small tasks to Codex (A/B): one lead request fewer on every task, 21/21, but total spend about even and 3.3× the tokens.

④ Delegation and choosing

ccx route picks who, which model and effort, or says doing it yourself is cheaper. Repository tasks: $0.063 vs $0.090 per success; small exercises: 3.1× the cost.

⑤ Checks and receipts

ccx re-runs your --check, another vendor reviews the diff, you give the verdict; the receipt says what the check covered. Right 29/30 on hidden tests; a check on the sub-agent's own tests passed all 18 of pg1's failures .

⑥ Control and recovery

ccx stop, ccx resume, ccx undo, --worktree, autonomy L0–L2. From a handoff alone the next agent picked up 3/3 in controlled runs; one real long session failed at first.

⑦ Measurement and honesty

One ledger across vendors, clean-environment checks, a public benchmark, negative results published. API-equivalent cost was 1.5 % from Claude's own on one run; on a subscription you pay in quota.

⑧ Interface and first steps

ccx ui: one project on one map; ccx demo with no account; ccx setup, ccx doctor. No user study yet; real use outside our own tests is thin.

Questions

Doesn't a second agent cost more tokens?

It can. On small tasks, a lead that answered as soon as ccx's check passed made one request fewer but spent about the same in total; a lead that reran the tests itself paid for the sub-task on top and waited longer. Most of the money goes on the lead re-reading its own conversation, which is what ccx lead, ccx sum and ccx fresh are for.

I'm on a subscription, not the API. Does this apply?

Yes. Costs are shown at API prices so runs can be compared; the dashboard also shows how much of each tool's quota went where. When one tool runs out, the work moves to the other (tested with stand-ins only so far).

Is it safe to let a sub-agent edit files?

Edits stay in the task's folder, every write run is snapshotted for ccx undo, and --mode read or --worktree keep your tree untouched. Details in SECURITY.md.

Which tools work?

Claude Code, Codex and DeepSeek (as dsh, or through Claude Code) can lead or work, tested for real. Gemini CLI is adapted from its docs but hasn't run for real, and only as a sub-agent; Kimi, GLM, Qwen and OpenRouter through Claude Code are configured, not tested.

Why the new name?

The old name, claude-codex-bridge, was nearly the same as another project's (SeemSeam/claude_codex_bridge), and it's no longer just two tools. The command is still ccx; the old address redirects.
