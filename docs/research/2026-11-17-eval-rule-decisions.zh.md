## 1. 额度场景以主导那家的自身花费为主指标

### 决定

- 对"派活能省主导那家额度"这类主张（额度场景：把长任务交给别家的子 agent），主花费指标是**主导那家的自身花费**：一个单元里所有打到主导所属厂商的调用
  （主导本身、同厂商子 agent、同厂商审查）的 API 等价美元，从账本汇总。这就是第二轮已经登记为次要指标的定义
  （[第二轮](prereg/2026-11-16-round2.zh.md) 第 4 节，#347 起由 `unified_summary` 计算）。
- **谁当主导就算谁。** 指标里不写任何厂商名：Codex 当主导就算 Codex 的花费，Claude 当主导就算 Claude 的。relayline 不偏向哪家，
  谁当主导由用户选。结论只对实际测过的"主导 / 子 agent"组合成立。
- 总花费（所有厂商合计，API 等价）留在判定里当**护栏**：总体贵太多就判不过。做对率和墙钟的护栏不变。
- 数字（2026-11-19 确认；每份预登记开跑前抄进去）：主导那家自身花费的每题几何平均比值，单侧 95% 上界 ≤ 0.6；护栏为总花费 ≤ 1.2 倍、
  做对率差的下界 > −0.15、墙钟中位 ≤ 3 倍。取值理由：0.6 要求明显省（G4 点估计 0.24，给新题上效应变小留了余地，但仍是"省一半左右或更多"）；
  1.2 倍是本项目以前用过的花费余量（[优化计划](2026-11-04-optimization-plan.zh.md) 第 3 阶段：每次成功花费 ≤ self 的 1.2 倍）；
  −0.15 是第二轮的非劣效界；3 倍给长任务的交接开销留空间（G4 实测 4.98 倍）。
- 其余花费类主张（默认不倒退、便宜首轮、更快）主花费仍是**总花费**。

### 理由和数据出处

- [统一测试](2026-11-14-unified.zh.md) 的 G4（8 道题，每题一次，用过的题，Claude 主导，Codex `gpt-6.1-sol` medium 子 agent）：
  self → ccxlong 做对 7 = 7；总花费 1.39 倍，按登记的总花费规则判 **Fail**；Claude 自身花费 $0.25 对 $1.03，**只有 self 的 24%**。
  当时的预登记对这个数没有门槛。
- 订阅用户用完的是主导那家的额度。总花费把另一家的花费也加进来，而那一份花的是另一家的额度；它回答"按 API 美元算便不便宜"，
  不回答"我主导那家的额度能不能撑更久"。两个问题要两个指标。
- 只有别家的子 agent 才能省主导的额度；同厂商子 agent 花的是同一份额度（第二轮 C 组的理由）。

### 这是开跑前换尺子，不是看了结果再改

- **G4 仍是 Fail**，不用新指标重判。它的 24% 只是提出这个问题的理由，不是答案的证据（8 道用过的题、每题一次、诊断组）。
- **第二轮不变。** 不管批准时 C 组跑没跑，C 组都按登记的判定（总花费 ≤ 1.0，主导自身花费为次要指标，诊断组，不改默认）。
- 新指标只用于批准后提交的预登记，并且用**没用过的新题**（计划约 60 道上游真实提交的长任务）。门槛在开跑前写进那份预登记，之后不改。

### 考虑过的替代方案

| 替代方案 | 为什么不用 |
|---|---|
| 仍只用总花费当主花费 | 量的不是用户会用完的那份额度；派给别家必然加上子 agent 的花费，"省额度"永远证明不了 |
| 主导自身花费和总花费都当主指标（都要过省钱门槛） | 同样的问题：总花费 ≤ 0.8 是另一个主张（总体更便宜）。总花费当护栏（≤ 1.2 倍）就保住了"不贵太多"，又不要求它省 |
| 直接量额度百分比（用量窗口） | 只有部分厂商、部分窗口有读数，而且不是按调用记的；账本美元每家每次调用都有 |
| 按订阅价格加权 | 订阅额度换算美元没有可靠办法 |
| 直接把指标写成 Claude 的花费（到目前主导都是 Claude） | 把指标绑死在一家；产品不偏向哪家 |

### 影响哪些预登记 / 报告

- 新的：下一份额度场景预登记（主指标和护栏）；之后别家当主导的对照。
- 不变：第二轮预登记及其 C 组、统一测试 G1–G4 报告、所有非额度类主张。
- 批准后另开文档 PR，在 `docs/engineering-standards.md` 的指标表里加一行"主导那家的自身花费"（不在本 PR 里）。

### 怎么回滚

后面写一条决定行撤回。已按本决定提交的预登记保留它的指标直到出判定（跑到一半不换尺子）；撤回只对之后提交的预登记生效。

## 2. 回执假阳性门槛：点估计 ≤ 2% 且上界 ≤ 5%

### 决定

- 普通 `ok` 回执而隐藏测试不过，算一次假阳性（定义不变，[工程标准](../engineering-standards.zh.md) 第 2 节）。对 `失败数 / n` 张普通 `ok` 回执：
  - **Pass**：点估计 `失败数 / n ≤ 2%`，**并且**单侧 95% Clopper-Pearson 上界 **≤ 5%**。
  - **Fail**：点估计 > 2%。
  - **Unknown**：点估计 ≤ 2% 但上界 > 5%（回执太少），或 n = 0。
- 方法：单侧 95% Clopper-Pearson（精确二项），和已合入的 `scripts/eval/receipt_fp.py`（#377）里的 `cp_upper` 一样。
  `ok_self_checked`、`done`、`UNVERIFIED` 照旧分开统计，不按这个门槛判。
- 哪些行合并成一个 `n`（比如同一个 pin 上几组的派活臂），在算回执数字之前写下来；只合并同一个 pin、同一套回执规则的行。
- **第二轮：** 批准时第二轮还没开跑，它报告里的回执分析就按本门槛；批准前已经开跑，就仍按旧写法（"≤ 2%"）并注明，本门槛最多作为标明的附加列出。
  两种情况下回执分析都不是第二轮任何一组的判定门槛。

### 理由

- 2% 门槛来自发版计划的 P1-10 项（[审计报告](2026-10-31-verdict-audit.zh.md)"对照门槛"一节引用）：#158 之后误报"对"超过 2% 是发版前必须修的问题。
  这个写法和工程标准的"≤ 2%"都没说是点估计还是上界。
  - 当点估计读：0/6 也算过，完全不考虑不确定性。
  - 当上界读：0 失败要 **149** 张回执（1 次失败要 236 张），没有哪次计划中的评测到得了，门槛永远判不了。
    `receipt_fp.py` 现在的 `below_2pct` 就是按这种读法。
- hc2 是 0/19：上界 14.6%。原写法下是"证明不了低于 2%"；新写法下是 Unknown，并且写明多大样本能判出来。
- 新门槛保留 2% 这个目标，另外限定 Pass 允许的不确定性有多大。

### 需要多大样本（用 `receipt_fp.cp_upper` 算）

| 失败数 | 能 Pass 的最小 n | 该 n 下的上界 | 对照：上界 ≤ 2% 需要的 n |
|---|---|---|---|
| 0 | 59 | 4.95% | 149 |
| 1 | 93 | 5.00% | 236 |
| 2 | 124 | 4.99% | 313 |
| 3 | 153 | 4.99% | 386 |
| 4 | 200 | 4.52% | 456 |

也就是：普通 `ok` 回执不到 59 张，结果只会是 Unknown 或 Fail，不会是 Pass。100 张最多允许 1 次失败，150 张最多 2 次，200 张最多 4 次。
第二轮 B 组 60 道题，派活臂最多约 60 张回执，其中只有一部分是普通 `ok`；要 Pass 多半得事先写明合并哪些行，或者等下一轮。

只作参考、不重判：hc2 的 0/19 普通 `ok` 按新规则是 Unknown。审计的 8/209 = 3.8% **口径不同，不可比**：它数的是回执"说对"的单元，
包括 `done` 和子 agent 自报的 `partial`（[审计报告](2026-10-31-verdict-audit.zh.md) 方法一节和"`partial` 带 `ok: true`"一条），不只是普通 `ok` 回执，
所以不对它套本门槛。

### 考虑过的替代方案

| 替代方案 | 为什么不用 |
|---|---|
| 上界 ≤ 2% | 要 149 张以上，以本项目的规模永远判不了 |
| 只看点估计 ≤ 2% | 0/6、0/19 都算过，而真实比例可能在 15%–39% |
| 下界高于 2% 才判 Fail | 对产品更宽松；维护者 2026-11-19 考虑后没有选（工程标准第 9 节：不选对结果有利的读法） |
| 双侧区间或 Wilson 区间 | 单侧对应问题本身（"最高可能多高"），也和已合入的脚本一致；精确法在小计数时稳妥 |

### 影响哪些预登记 / 报告

- 批准后写下的每一个回执假阳性判定（第二轮按上面写的办）。新规则只是在它澄清的"≤ 2%"上多加一个条件，不可能把 Fail 变成 Pass。
- 批准后的后续（各开 issue 和 PR）：`receipt_fp.py` 在 `below_2pct` 旁边加一个按本门槛判的字段（已有字段含义不变）；
  工程标准的"回执假阳性"一行引用本门槛。不在本 PR 里。
- 不变：STATUS、measured、hc2 和审计报告。

### 怎么回滚

后面写一条决定行撤回；已写下的判定保留当时的规则，并注明按哪条规则判的。

## 3. "额度用完不断工"的证据定义

### 决定

这个主张没法做成预登记的对照实验：没人会故意烧额度。所以按**自然发生的**限额事件记录来判。证据等级：measured，但不是对照实验；报告里要写明。
下面每个条件都标明**机器**（能从 ccx 自己的记录查）或**人工**（要用户当时写下的记录）。`N` 是接续时限，**4 小时**（维护者 2026-11-19 确认）。

**什么算一次事件。** 每个原始任务算一次；继承了前一次运行字段的审查修复轮和续跑不算新事件。

| 来源 | 算的条件 | 怎么查 |
|---|---|---|
| 子 agent 在 `ccx run` / `batch` / `q` 里撞额度 | 运行记录有 `quota_stop`、或 `quota_fallback`、或某次尝试 `kind == "quota"`：和每日使用页（`ccx/daily.py`，#376）的"撞限"口径一样。改没改派都算 | 机器 |
| 主导撞到已确认的上限（Claude `StopFailure` 钩子，`ccx relay capture --hook`） | `.ccx/relay/` 里有一个 `state = quota_stopped` 的 packet | 机器 |
| 主导撞到未确认的上限 | `rate_limit_unconfirmed` 的 packet **只能**通过这条事先定好的人工途径计入：packet 出现后 1 小时内、在知道接续结果之前，用户在记录里写下用量读数显示窗口已用完，或重置时间至少在 1 小时以后（来自 `ccx quota`、CLI 自己的用量界面或限额提示），并附 packet id。没有这条记录就不计入 | 人工，事先定好 |

不计入、但列出次数：没有上面那条记录的 `rate_limit_unconfirmed` packet；`capacity_recovery`（模型忙，不是额度）；
模拟或回放的事件（比如 [relay](../relay.zh.md) 里 2026-11-10 那次检查）；评测 hub 里的事件（`ledger.is_eval`）；任何故意制造的事件。

真实的 Claude `StopFailure` 多半是 `rate_limit_unconfirmed`（`ccx/quota_signals.py`；[relay](../relay.zh.md)）。**所以主导事件可能长期为 0。**
那时主张只对子 agent 报告，并写明主导一侧是 Unknown。

**成功**（没断工），下面都要满足：

1. **从这次事件接着做**（机器）。子 agent：同一个运行通过 `quota_fallback` 继续，或者之后有一个 `resumed_from` 指向事件运行的运行在另一家或另一模型上启动。
   主导：事件 packet 有接续记录 `.ccx/relay/<packet id>.continue-*.json`，且 `state` 不是 `prepared` 或 `interrupted`（由用户敲
   `ccx relay continue ... --launch` 是设计如此）。
2. **N 小时内**（机器，有一处限制）。子 agent：从事件运行的 `ts` 到接续运行开始，查账本。主导：packet 和接续记录没有时间字段，用文件修改时间；
   文件被复制或改动过的，这一条转为**人工**。
3. **没丢东西**（能机器就机器）。主导：接续记录的 `workspace_changed` 为 `false`（ccx 拿启动时的快照，包括脏文件 `content_fingerprint`，和 packet 里的比）。
   为 `true` 或指纹 `Unknown` 时，由用户核对 packet 文件清单里的改动没有丢（**人工**）。子 agent：接续继承的是事件运行的 worktree / 写入快照
   （续跑继承所接运行的快照；改派是同一个运行）。
4. **不是从头重做**（机器）。从事件到接续之间，同一工作区里没有另起一个同标签、`resumed_from` 为空的运行；（主导）也没有改用同一会话的另一个 packet 接续。
5. **做完了**（机器或人工）。子 agent：接续运行以 `ok` 结束，之后没被 `ccx verify` 改判为错。主导：接续以 `exited`、退出码 0、`changes_observed` 为真结束，
   并且从接续结束起 N 小时内用 `ccx verify` 或在每日记录里标记做完（**人工**）。

**失败**：计入的事件里不算成功的。特别是：`quota_stop` 之后既没改派、N 小时内也没有接续；packet 没法接续（比如 Git 快照 Unknown）；
接续以 `no_changes`、`changes_unknown` 或出错结束、之后活是重做的；活放弃了。**任何一次事件丢了未提交的改动，整个主张直接判 Fail**，不看比例。

**未尝试**：用户选择等额度重置，并当时写进每日记录。列出次数，不计入比例（维护者 2026-11-19 确认）。

**多少次才下结论**：至少 **5 次计入事件**，成功率 ≥ **80%**（5 次里 4 次、10 次里 8 次）。不到 5 次是 Unknown。
报告写成功数 / 计入事件数、单侧 95% Clopper-Pearson 下界（4/5 约 34%，证据很弱，要照实标注），并按角色（主导 / 子 agent）
和厂商组合分开列。对外引用数字要两个互不重叠的时段、各至少 5 次事件、都 ≥ 80%（工程标准的两轮规则）。

### 理由

- [relay](../relay.zh.md) 现在只有工程检查：假 CLI、捕获并脱敏的 Claude 事件、一次模拟的 `StopFailure`（2026-11-10）。
  从没记录过一次真实撞限。STATUS 把这一条列为未验证。
- 只数改派（`quota_fallback` 只在找到改派对象时才写）会把接力失败的事件漏出分母；每日使用页的"撞限"口径把每次撞限都算上。
- 不在事件发生前写好定义，事后怎么数都能各说各的。

### 考虑过的替代方案

| 替代方案 | 为什么不用 |
|---|---|
| 在对照实验里故意把额度用完 | 花的是用户的额度，也不是自然行为；relay 文档也写了不要这样做 |
| 只数带 `quota_fallback` 的运行 | 偏向成功：撞限而没改派写的是 `quota_stop` |
| 每个 `rate_limit_unconfirmed` 都算 | 很多只是短暂限速，会用不需要接力的事件撑大分母 |
| `rate_limit_unconfirmed` 一律不算 | 主导事件可能永远凑不出；事先定好的人工途径让它能计入，又不靠事后判断 |
| 把 `capacity_recovery` 也算进去 | 模型忙是另一种失败；放在旁边报，不混进来 |
| 继续只写"Unknown"、不给定义 | 永远判不出来；而这是用户的主打定位之一 |

### 影响哪些预登记 / 报告

- 计划中的真实日常使用期：每日使用页（#376）已经统计撞限和接力；其余字段（接续、N 小时时限、人工记录）按事件逐条记。
- 已知缺口：Codex 没有额度 `StopFailure` 钩子（[relay](../relay.zh.md)），Codex 当主导时撞限不会被自动记下；这类事件除非带证据手工记录，否则是 Unknown。
- 不变：`[relay] enabled = false` 默认值、额度分类、所有命令和 JSON 字段。

后面写一条决定行撤回；已记下的事件保留，并按记录时的定义报告。
