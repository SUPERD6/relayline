## 2. 问题

编码 agent 现在会互相派活：主 agent（Claude Code 或 Codex）把任务的一块交给更便宜或不同的子 agent，问题是这样做是否比主 agent
自己做更好。有四件事让这个问题难答，各对应本报告的一节：

1. **子 agent 不知道主 agent 知道的事。** 主 agent 对话里早先定下的决定，或记忆里的一条笔记，对全新的子 agent 不可见。在专为需要它而设计的题上，
   没有它便宜的子 agent 几乎总是做错（6.1 节）。
2. **验收不能只靠子 agent 自己的报告。** worker 说"做完了"，或它自己挑的一次测试通过，都可能是错的。
3. **对比本身很容易做错。** 委派通常和"自己做"的基线比，而基线的成本和质量取决于它怎么跑。本项目的工作假设是：
   把基线当作*全新的短会话*来跑，会低估在*真实长会话*里自己做的成本，于是委派显得比实际更差（或更好）。
   **这个假设在本文没有被检验**：B 组冻结的设计（自己做 vs 便宜先行，7.1 节）没有长会话组，需要另行预先登记一次测量。
4. **会话会中断。** 额度用完会让主 agent 停在半路；工作应能在另一个工具里接着做，而不是从头来（接力，4.3 节）。

### 3.1 最近的一篇：arXiv 2611.33893

*When Are Parallel Subagents Effective for Coding?*（Lyu、Yin、Zhang；[arXiv:2611.33893](https://arxiv.org/abs/2611.33893)，
2026-11）。就摘要所说：它在 NL2Repo 和 ProgramBench 上，按等时间、等成本比较单 agent 与"主 agent + 子 agent"；报告子 agent
只比单 agent 多一点、成本更高；报告单 agent"定期开新空会话"比"一直续同一个会话"早期进展更快；还报告一句提示（"先探测参考程序"）
就能拿回大部分收益。它是最近的一篇，与我们主线重叠一半。

| | 2611.33893（据摘要） | 本工作 |
|---|---|---|
| 问题 | 仓库构建里并行子 agent 何时值得 | 派给更便宜的子 agent 是否优于自己做，以及它为什么会失败 |
| 变量 | 单 agent 对"主 + 子"；会话长度和新鲜上下文作为单 agent 基线的因素 | 给子 agent 什么（共享上下文、记忆）；谁先做（便宜先行 vs 自己做）；怎么验收 |
| 结果指标 | 仓库构建进度，等时间、等成本 | 每题隐藏测试的正确性（配对），加每次成功的成本和用时 |

## 4. 系统

relayline（命令 `ccx`）让 Claude Code、Codex 和 DeepSeek 互相当主 agent 或子 agent。Python 3.11+，只用标准库。
细节见 [DESIGN](../DESIGN.zh.md)；本节只写评测要检验的部分。

### 4.1 带共享上下文和记忆的委派

- **委派。** `ccx` 无头运行另一个工具，读取一份紧凑的 JSON 结果；完整日志留在磁盘。失败或受阻的运行升一档；额度失败回退到另一个
  agent（[DESIGN](../DESIGN.zh.md)，"组成"第 1 项）。
- **共享上下文**（`--context on`）：把子 agent 需要的主 agent 近期对话附在任务简报上（[shared-context](../shared-context.zh.md)）。
  A1 / A1x 检验的就是它。
- **共享记忆**：增量、只追加的笔记库；子 agent 的简报只带与任务有共同词的笔记（[DESIGN](../DESIGN.zh.md)，"组成"第 5 项）。
  A2 / A2x 检验的就是它。
- **便宜先行**（`dispatch.cheap_first`）：从最便宜的一档开始，失败再升档（[dispatch](../dispatch.zh.md)）。B 组检验的就是它。

### 4.2 可靠性层（回执）

一次委派返回一份*回执*：worker 的状态、ccx 自己的检查（`--check`）、可选的独立审查，并把"执行成功"和"验收通过"分开记。
我们自己的审计显示了它哪里弱，这里如实写出而不是回避：

- 一个没测到所要求行为的检查通过了，错误的工作被放行；审计量出了这个比率（[verdict audit](2026-10-31-verdict-audit.zh.md)）。
- 执行成功和验收是两个不同的标志，紧凑结果在验收失败时仍可能给出 `ok=true`、退出码 0，评测提示又把 `ok` 当作验收；
  已加入 `headline` 字段，它是否改变主 agent 的行为是 Unknown（[receipt audit](2026-11-05-receipt-audit.zh.md)）。
- 主 agent 的 `--check` 是整套已有测试时，它看不到新要求（[统一测试报告，"为什么 G3/G4 差"](2026-11-14-unified.zh.md)）；
  已加入灵敏度检查（默认关闭）。

### 4.3 跨工具接力

某个工具因用量上限停下时，钩子保存一份交接包；用户停掉旧会话，再运行一条命令在另一个工具里继续同一任务（[relay](../relay.zh.md)）。
接力**默认关闭，属实验性**。TODO：接力主张（"工作不中断"）要用至少 5 次自然触顶来判，额度成本主张用主 agent 厂商花费来判

## 5. 评测设计

规则在每一轮之前的预先登记里定死。读结果时要紧的几点：

- **先登记。** 任务、分组、阈值和判定规则在任何一次运行前提交（[第一轮](prereg/2026-11-07-unified.zh.md)、
  [第二轮](prereg/2026-11-16-round2.zh.md)）。偏离以变更日志条目记录，不悄悄改掉。
- **单位与检验。** 每题每组跑一次，题是单位。配对组用隐藏测试结果做精确双侧 McNemar 检验，每个主张族内用 Holm 校正
  （[第二轮，"测了什么、怎么测"](2026-11-27-round2.zh.md)）。
- **隐藏测试。** 正确性由主 agent 和子 agent 都看不到的测试打分。
- **通过规则（A 组）。** 有效配对 ≥ 48 中的 43、有该功能比没有时做对的题更多、校正后 p < 0.05、效应至少 0.15
  （[第二轮](2026-11-27-round2.zh.md)）；共享上下文组另有每次成功成本的上界。
- **一次一组，机器空闲。** 只读监控确认一组运行期间没有外部 pytest；被打断的组不续跑，换新标签从头重跑
  （[第二轮](2026-11-27-round2.zh.md)、[第一轮"判 Unknown 后重跑的尝试"](2026-11-14-unified.zh.md)）。
- **泄漏审计。** 第一轮之后的只读审计发现一个组被污染；该结果被撤回并公布为 Unknown（[第一轮，"更正"](2026-11-14-unified.zh.md)）。
- **统一记账单位。** API 等价美元，主指标是每次成功的成本（[token 成本量化](2026-10-23-token-cost-quantification.zh.md)）。
- **解读规则。** 一轮只是信号，引用数字要有第二轮（[第二轮](2026-11-27-round2.zh.md)，"怎么理解这些数"）。

### 6.2 哪些不算赢

- **成本。** 各组总花费相近：有上下文时 A1 更低、A1x 更高。每次成功的成本下降主要是因为基线几乎从不成功，所以不声称有节省
  （[第二轮，"局限"](2026-11-27-round2.zh.md)）。
- **第一轮的便宜先行和长任务没过。** G3（便宜先行，6 题）和 G4 长任务诊断没过各自的规则：自己做 3/6 对、便宜先行 2/6 对，
  成本 0.60×，用时 2.72×（[第一轮](2026-11-14-unified.zh.md)）。调查把很大一部分原因归到一个看不到新要求的检查，以及自己做约 40 秒就能完成的
  任务上交接的额外开销（[第一轮，"为什么 G3/G4 差"](2026-11-14-unified.zh.md)）。
- **外部小练习：委派输了。** 在 30 道 polyglot Python 练习上，委派的主 agent 做对 12/30，自己做 25/30，每次成功还更贵
  （[pg1](2026-10-31-polyglot-pg1.zh.md)）。
- **仓库留出集上有利，但有限制。** 在建 ccx 时没用过的 10 道题上，委派没有被看出更不正确，每次成功更便宜，用时约为自己做的 3 倍；
  一半题目来自本仓库，答案可能泄漏（[hc1](2026-10-29-hc1-holdout.zh.md)）。
- **长会话（P4）没过**成本和用时两道门，按记录的行；历史上的换行检查污染使因果无法干净解读（[优化结果](2026-11-05-optimize-results.zh.md)）。
- pg1、hc1、P4 用的是更早的规则和代码，不在第二轮的预先登记之下，也不是配对的。

### 6.3 回执："做完了"有多可靠？

修复 #158 之后，209 份说"对"的回执里有 8 份没过隐藏测试（3.8%，Wilson 95% 区间 2.0–7.4%；没达到事先定的 2% 线），51 份说"错"的回执里有 47 份其实是对的，所以在那次审计的样本里
ccx 的错误更多是太严而不是太松（[verdict audit](2026-10-31-verdict-audit.zh.md)）。pg3b 的复查方向相反：ccx 自检算对的 29 份回执里
15 份没过隐藏测试，而审查把 29 份全放行，并且无法测 2% 线（[pg3b](2026-11-03-pg3b-receipts.zh.md)）。这次审计早于第一轮、第二轮评测，没有在它们之下重做；TODO：用后续轮次的数据重做。
