## Why a second round

Round 1 (2026-11-11 to 11-13) gave G1 shared context Pass, G2 memory Pass, G3 cheap first round Fail, G4 long tasks
Fail. Its own limits (report, section "Limits") are what this round fixes:

| Round 1 limit | Round 2 answer |
|---|---|
| All tasks used before, best-case designs | Only new tasks, harder by construction, frozen before any run (section 2) |
| Repeats of a task are not independent, p-values optimistic | One run per task per arm; the task is the unit of analysis; more tasks instead of repeats (section 3) |
| G3 had 6 tasks, G4 8: one task flips a verdict | Sample sizes from a power analysis: 48 / 48 / 60 tasks (section 3) |
| G3's actual first rung (gpt-6-luna/low) was not the one written down, and the dry-run did not print it | The dry-run must print the default first rung; it is copied into the report and checked against the ledgers; a mismatch makes the group Unknown (B) |
| Only total spend was judged; no Claude-spend metric | Claude's own spend is a pre-registered secondary metric (section 4) |
| The lead's `--check` was the existing suite, blind to the new requirement | Group B uses `[check] sensitivity = "escalate"` and a lead prompt that follows #326 (write a failing check first) |
| Handover overhead dominated 40-second tasks | Harder tasks in B; group C uses long tasks where the overhead can amortize |

## 1. Groups

Run order: A1 → A2 → A1x → A2x → B → C. **Which groups run is decided now, before any run:** all six are part of
this pre-registration and run regardless of each other's results; none is added or dropped after seeing a result. The next group starts
after the previous group's summary is archived.

### A1 Shared context on new tasks

- Factor: `--context on` vs `off` (unchanged from round 1).
- Sub-agent: Claude `haiku` low (the shipped T1 Claude rung), `--from claude --to claude`. Question: does the lead's
  context help a cheap sub-agent **from the lead's own vendor**? Round 1 measured it only on Codex and dsh, so this is
  the first measurement with a same-vendor sub-agent. The Codex replication is A1x.
- Tasks: 48 new **settled** tasks (the lead transcript contains the agreement the hidden test checks) + 8 new
  **neutral** tasks (the transcript has nothing relevant; harm check only, not in the primary test). Section 2.
- Runs: 1 per task per arm. Primary: 48 settled pairs. Total units: 56 tasks × 2 arms = 112.
- Command (after #345): `python scripts/eval/strength_retest.py execute context --tasks <A1 task file> --reps 1
  --agents claude --run --budget 5 --unit-budget 0.15 --claude-home <CLAUDE_HOME> --out <eval dir>/r2-a1`
  (exact flag spelling follows the merged #345; the dry-run output is archived first).
- Summary: `unified_summary.py strength <dir> --pair on,off` restricted to settled pairs (b = on right and off
  wrong, c = the reverse).
- Verdict, decided only after A2's summary exists (Holm needs both p-values), in order:
  1. Valid settled pairs < 43/48 → Unknown.
  2. b > c, Holm-adjusted exact McNemar p < 0.05 (two-sided; family A1 + A2), (b − c)/n ≥ 0.15, and on cost per
     success ≤ 1.2× off (not applicable when off has 0 successes) → Pass.
  3. Otherwise Fail. An off arm near ceiling (tasks that turn out not to need the context) is still Fail by rule 2,
     with the ceiling noted; no rescue.
- Change from round 1: round 1 required b − c ≥ 15 for 42 pairs; with 48 independent tasks this is written as a
  rate, (b − c)/n ≥ 0.15, so the effect-size floor does not depend on n.

### A2 Memory on new tasks

- Sub-agent: Claude `haiku` low, same reason as A1 (`mem delta --as claude` for hubstart). The Codex replication is A2x.
- Tasks: 48 new memory tasks; same distractor notes in every arm. Section 2.
- Runs: 1 per task per arm: 48 × 4 = 192 units. Primary: 48 pairs mem vs nomem.
- Command (after #345): `python scripts/eval/strength_retest.py execute memory --tasks <A2 task file> --reps 1

- Summary: `--pair mem,nomem`.
- Verdict: valid pairs < 43/48 → Unknown; b > c, Holm-adjusted exact McNemar p < 0.05 (two-sided) and
  (b − c)/n ≥ 0.15 → Pass; otherwise Fail. (Round 1 had no cost condition for memory; none is added.)

### B Cheap first round v2 vs self

- Factor: who does the work. Arm `self`: the lead (Claude Sonnet medium) implements and checks alone. Arm
  `ccxcheapfirst2` (#346): the same lead delegates to a **Claude** sub-agent (`--to claude`) through ccx with
  `dispatch.cheap_first = true` and `[check] sensitivity = "escalate"`, and its prompt follows the shipped #326/#338
  delegation guidance (write at least one test for the new requirement, see it fail, pass it as `--check`, put
  concrete inputs and outputs in the brief). Review, routing and everything else stay at the shipped defaults.
- Why this is one factor: `escalate` acts only under `cheap_first`, and the #326 guidance is how the shipped skill
  tells a lead to use `--check`; the eval lead does not load skills, so the prompt carries it. The three are tested
  as one package against self and **cannot be separated** in this design; a Pass says the package works, not which
  part does. Round 1's `ccxcheapfirst` arm is not rerun (its result stays historical).
- Question: does cheap-first delegation with a sensitive check save cost without losing correctness when the cheap
  and escalation rungs are the lead's own vendor's models? Round 1's G3 asked it with Codex; this asks it within one
  vendor, so the result is about the cheap-first mechanism, not about switching vendors. With `--to claude`, ccx's code gives first rung T1 `claude:haiku:low` and the requested
  rung the shipped default (T2 `claude:sonnet:medium`, the lead's own model); the dry-run must confirm both. The
  shipped review picks a reviewer from the other vendor, so a **Codex reviewer** takes part; this is kept because it
  is what a user gets by default, and the dry-run prints the reviewer, which goes into the report.
- Scope of the conclusion: B covers `--to claude` only. Under the engineering standards' "at most two improvement
  rounds", B is cheap-first's **first** improvement round whatever the sub-agent's vendor; a later cheap-first
  evaluation with Codex would be the second and last.
- Sub-agent rungs: before the run, the dry-run's `default_first_rung` (model and effort, #346), the reviewer and the
  effective settings per arm are copied into the report. After the run the observed first rung of every delegated
  unit is read from the ledgers (#347).
- Tasks: 60 new harder tasks (section 2), one run per task per arm, 120 units. The two arms alternate who runs first.
- Caps: equal per-task ceilings. `self` gets a lead cap of $1.5; `ccxcheapfirst2` gets lead $0.5 + delegation $1.0
  (`--self-lead-budget`, #355). A unit that hits its cap keeps its hidden-test outcome and its recorded spend, like
  any other row; the number of cap hits per arm is reported.
- Command (flags as merged in #355/#358): `python scripts/eval/p4_long_session.py --run --split r2b
  --tasks-file <B selection> --tasks-sha256 <its SHA-256> --arms self,ccxcheapfirst2 --child-agent claude
  --max-escalation-rate none --max-invalid-rows 3 --budget 34.5 --max-operational-usd 36 --self-lead-budget 1.5
  --lead-budget .5 --child-budget 1 --tag r2-b --pin-commit PIN --ext-cache <EXT_CACHE> --ext-python <EXT_PYTHON>
  --codex-home <CODEX_HOME> --out <eval dir>/r2-b.jsonl --wait-quiet 10` (`--codex-home` is for the reviewer; the
  dry-run is archived first, and its `tasks_file_sha256`, `default_first_rung`, `reviewers`, `network`, `stop_rules`
  and `arm_settings` go into the report). The script reserves a task's caps ($1.5) before starting it and needs
  "spent + reservation ≤ budget", so the worst case is budget + one reservation = $36; `--max-operational-usd 36`
  refuses to start if that envelope is larger. Rows record `first_rungs`, `first_rung_matches_default`,
  `lead_check_commands`, `cap_hit`, `invalid_reason` and `reserved_usd`.
- Summary: `unified_summary.py p4 --tag r2-b --out <eval dir>/r2-b.jsonl --pair self,ccxcheapfirst2` (A = self).
- Verdict, on valid task pairs (the env_clean subset is reported too), in order:
  1. Unknown if any of: valid task pairs < 54/60; more than 3 units with unknown cost; any delegated unit's observed
     first rung differs from the dry-run's `default_first_rung`; more than 3 units without dispatch evidence; the
     group was stopped (section 5) or by its budget.
  2. Pass if all four hold (an intersection–union test; each part at its own level, no adjustment needed):
     - **Correctness non-inferiority**: the one-sided 95% lower bound (Tango score interval) of
       p(ccxcheapfirst2 right) − p(self right) is > −0.15;
     - **Per-task cost**: the one-sided 95% upper bound of the per-task geometric-mean cost ratio
       (ccxcheapfirst2 / self, paired t on log ratios) is ≤ 0.8;
     - **Total cost**: total spend ccxcheapfirst2 / self ≤ 0.8 (point rule, round 1's definition; the geometric mean
       weights tasks equally and can pass while a few expensive tasks make the total worse, and the total is what a
       user pays);
     - **Wall time**: median wall time ccxcheapfirst2 / median wall time self ≤ 2 (round 1's definition).
  3. Otherwise Fail.
- Escalation: round 1's "stop the group when escalation rate > 30%" is not used here (`escalate` raises escalation by
  design; its cost is judged by the cost rules). The escalation rate is reported.
- Changes from round 1: correctness was "right ≥ self" as a point rule on 6 tasks; it is now a non-inferiority bound
  with margin 0.15 on 60 tasks. The total-cost and wall rules keep round 1's formulas but are computed on valid pairs
  (round 1 used all rows); the all-rows version, with invalid rows counted as wrong and charged at their reservation,
  is a pre-registered secondary analysis. The per-task cost bound is added.

## 2. Tasks: source, difficulty and leakage

**None of the tasks may have appeared in any earlier evaluation.** The leakage check of #348 scans every task
definition and selection file under `scripts/eval/` (all `*.py` and `*.json`, not only `tasks_*.py`) and
`docs/research/data/`. A new task is replaced before freezing if it has the same repository + commit as an old one,
or if its normalized brief has a `difflib.SequenceMatcher` ratio ≥ 0.6 with any old brief. The task-set PR lists
every candidate above 0.4 with its score.

### B and C: upstream commits first, then new authored tasks

1. **Upstream commits** (selected by the #348 script, rules fixed here before running it):
   - **Repository list, mechanical:** the hugovk "top-pypi-packages" 30-day download ranking, the snapshot dated
     closest before 2026-11-16 (file and SHA-256 committed in the task-set PR). Walk it in rank order and keep a
     package when its source is a public GitHub repository under MIT, BSD, Apache-2.0, ISC or PSF, it is pure Python
     (no compiled extension in the repository), its pytest suite runs offline on the parent within 10 minutes with
     dependencies installable into `--ext-python` from a cache that the #348 script fills automatically from the list
     (not by hand), and it is **not used before** (more-itertools,
     boltons and every repository in earlier selection files are excluded).
   - Commit date (committer time, `%ct`) **on or after 2026-07-01**, to reduce the chance the models saw the change in training. The
     vendors' training cut-offs for the pinned models are not all published; this is a mitigation, not a guarantee,
     and the report states it.
   - Implementation change ≥ 60 lines or ≥ 3 code files (C: ≥ 150 lines or ≥ 5 files); tests, docs and `.pyi` do
     not count.
   - **Hidden tests** = tests added or changed by that commit, of which at least one fails on the parent (a pytest exit
     code of 1, or 2 for a collection error such as importing a module the commit adds) and all pass on the commit;
     the existing suite passes on the parent. Following #364, commits that change test support files (conftest,
     helpers, data) or delete or rename tests are excluded. A repository with a `src/` layout is kept only if at `PIN`
     the P4 scorer puts `src/` on the path as the selection's validation does (#367); otherwise src-layout repositories
     are excluded. The selection runs only after #364 is merged; the snapshot's date is recorded by hand in the change
     log, since the script does not check it. This makes "the existing suite" blind to the new
     requirement, exactly round 1's failure mode.
   - Fixed order: repositories in rank order, commits by time descending within a repository, SHA as tie-break.
     **At most 6 tasks per repository for B and at most 4 for C**, counted separately (each group is analysed on its
     own; within a group no repository exceeds its cap). B takes the first 60 qualifying commits; C takes the next 24
     that meet C's size rule. Every exclusion and its reason is written to the selection JSON.
   - Briefs: written from the commit message and the diff by an author session that takes no part in any run;
     a fresh reviewer checks that the brief states each requirement the hidden tests check (a trace table: every
     hidden assertion → one brief sentence) and does not paste test literals.
2. **Authored tasks**, only to fill the count when step 1 yields too few (the report states how many of each):
   - Written by a session that takes no part in any run (model recorded: Opus 5.5), in a fresh small repository,
     each with a reference solution and hidden tests.
   - Harder by construction: a change across at least two modules, or a behavior that conflicts with the obvious
     default, plus at least one edge case named in the brief.
   - Validated offline by #348: hidden tests fail on the start tree and pass on the reference; the existing suite
     passes on the start tree; trace table complete.
   - Because the author is a Claude model, the source (upstream / authored) is a stratum in the secondary analysis,
     as is the repository.

### A1 and A2: new synthetic tasks

- Written by a session that takes no part in any run, with the same trace-table check. Each task's hidden test
  checks both the function and the agreement / remembered convention.
- Harder than round 1 by construction: (a) the convention conflicts with what the repository's style suggests,
  (b) two or three conventions per task, all checked, (c) in A1 at least a third of the transcripts revise an
  agreement mid-conversation (the latest one counts), (d) distractor notes on neighboring topics.
- A1's 8 neutral tasks contain no relevant agreement (harm check: report c − b on them).

### Freezing and defects

- All task files, hidden tests and selection JSONs go into one task-set PR, with an SHA-256 manifest (#348); the
  change log records the manifest hash before any run, and `PIN` includes that PR.
- Hidden tests and reference solutions stay out of the unit's working tree until the CLI exits (current runners).
- A development set of 4 extra tasks per group (A1, A2, B; C uses 2 of its own) is used for smoke runs, script
  debugging and measuring unit costs (section 7) only, and never enters any analysis.
- **No task is changed or dropped after the first model call.** A task found defective afterwards (e.g. a hidden test
  contradicts its brief) stays in the primary analysis as is; the report flags it and may add a secondary analysis
  without it. This leaves no way to improve a result by removing tasks.

## 3. Power analysis and sample sizes

The unit is the task: one run per task per arm, so pairs are independent if tasks are (B and C cap tasks per
repository; C uses one episode per task). Calculations: exact enumeration for McNemar; 4 000–20 000 simulations for
the others (standard library; the script is in this PR's description; the independent review recomputed the
numbers).

| Group | Test | Assumed effect | Level | Power at the chosen n | Chosen n |
|---|---|---|---|---|---|
| A1, A2 (and A1x, A2x) | exact McNemar, two-sided | p(on right, off wrong) = 0.40, reverse 0.05 (about half of round 1's 16/21 codex; there is no round-1 number for Claude Haiku, so this is an assumption) | 0.025 (Holm's stricter step) | 0.94 | **48** |
| same | same | smaller effect: 0.30 / 0.05 | 0.025 | 0.75 | 48 |
| B | Tango lower bound > −0.15 | true difference 0, discordant 10% / 20% / 30% of tasks | one-sided 0.05 | 0.95 / 0.80 / 0.67 | **60** |
| B | same | true difference −0.05, same discordance | one-sided 0.05 | 0.70 / 0.51 / 0.40 | 60 |
| B | GMR upper bound ≤ 0.8 | true GMR 0.60, SD of log ratio 0.5 / 0.8 | one-sided 0.05 | ≥ 0.99 / 0.87 | 60 |
| B | same | true GMR 0.70, SD 0.5 / 0.8 | one-sided 0.05 | 0.66 / 0.36 | 60 |
| C | as B, cost limits ≤ 1.0 | as B | one-sided 0.05 | correctness 0.58 / 0.42 / 0.34 at 10% / 20% / 30% discordant; per-task cost bound ≤ 1.0 about 0.92 (GMR 0.60, SD 0.8) | 24 (budget; diagnostic) |

- **The cost assumptions for B have no direct basis.** Round 1's G3 (GMR 0.45, SD 0.61) used a Codex sub-agent; with
  a Claude sub-agent the escalation rung is the lead's own model, so escalated tasks can cost more than self. The
  table therefore shows GMR 0.70 as well. The dev-set measurement (section 7) is reported next to these assumptions.
- **Overall power of B** (all parts must pass): about 0.80 × 0.87 ≈ 0.70 at 20% discordance, GMR 0.60, SD 0.8, before
  the total-cost and wall rules; lower if the true cost ratio is near 0.8. B is designed to detect a clear saving, not
  a marginal one.
- A smaller n was checked and rejected: A at 36 tasks gives 0.58 under the smaller effect; B at 48 gives 0.73 at
  20% discordant. B's margin 0.10 was checked and rejected: at 60 tasks its power is 0.41–0.72.
- Repeats: none. A second run of the same task adds little information for a task-level claim and is not
  independent; the budget goes to more tasks instead.
- B's margin 0.15 means "at most 15 points less often right"; that is the price of a feasible sample. It is not a
  claim of equal correctness, and the report must say so next to the number.

## 4. Statistics

- **Pairing**: by task in every group. Only pairs valid on both sides count.
- **Primary tests**: A1, A2, A1x, A2x: exact McNemar (two-sided, with b > c required). B, C: Tango score interval for
  the paired difference in correctness, one-sided 95% lower bound; paired t on per-task log cost ratios, one-sided 95%
  upper bound; total-cost ratio and median-wall ratio (point rules).
- **Multiplicity**: A1 and A2 form one family, Holm at familywise α = 0.05; A1x and A2x form a second family (the
  round-1 Codex claims), Holm at 0.05. Both families and both their runs are fixed here before any run, and they
  answer different claims (Claude sub-agent / Codex sub-agent); neither family's result changes the other's verdict.
  **If one group of a family is Unknown, its p-value counts as 1** (the other group is then judged at 0.025), and no
  verdict of a family is written until both its summaries exist. B is one intersection–union test (all parts must
  pass, so no adjustment is needed within it). B and A answer different claims about different settings and are not
  pooled; C is diagnostic. Secondary metrics are descriptive, with unadjusted 95% intervals labelled as such; none of
  them can turn a primary Fail or Unknown into a Pass.
- **Secondary metrics** (reported for every group where they apply; no gate):
  - **Claude's own spend**: per arm, the spend of every Claude call in the unit (lead, Claude sub-agents, Claude
    reviewers), summed by vendor from the ledgers (#347), and the per-task geometric-mean ratio with its 95% interval.
    It is the cost to the user's Claude quota. In B both arms are almost all Claude, so it is close to total spend;
    in C it separates the lead from the Codex sub-agent. Total spend stays the primary cost.
  - Correctness rates with numerators and denominators; cost per success; cumulative and median wall time; cap hits
    per arm (B, C); escalation rate and first-rung vs escalation spend (B); share of checks the sensitivity receipt
    marked as already passing before the change (B); Codex reviewer spend (B); hubmem/hubstart (A2, A2x); neutral
    harm check (A1, A1x); strata by task source and by repository (B, C); env_clean subset; B's cost bounds
    recomputed with unknown-cost units charged at their reservation.
- Ties and zeros: no finite cost per success when an arm has 0 successes.

## 5. Interruption and reruns

As in round 1, plus the invalid-row rule in section 0:

- The scripts cannot resume. A group that is stopped keeps every completed row, its spend counts toward the total,
  and it is **Unknown**; it is never resumed.
- **Who may stop a group:** only the script's own stop rules (budget, more than 3 unknown-cost or no-dispatch-evidence rows, its environment check) or
  the operator for a listed cause: another evaluation or pytest running on the machine, a reboot or crash of the
  machine, a CLI version change, or known spend above the runtime upper bound. No other manual stop. Every stop is
  written into the change log with its cause and the number of completed rows, and the stopped attempt's rows are
  listed in full in the report.
- If the cause is an infrastructure fault, it is fixed in its own PR; the group is rerun **from the start** on a new
  pin with a new tag / output directory, recorded in the change log (cause, fix PR, new pin) before the rerun. No
  threshold, sample or task changes on a rerun. The files of the stopped attempt are kept.
- If the cause is the machine, rerun from the start without a code change, same rule.
- At most two reruns per group; after that the group is Unknown and the lead stops and asks the user.

## 6. After a verdict

- **A1/A2 Pass**: shared context / memory have a first Pass on a Claude sub-agent (one round is a signal; quoting a
  number needs a second round). **A1x/A2x Pass**: together with round 1, the Codex claims have two Pass rounds and
  may be quoted with both reports. Any default change still needs its own decision note.
- **B Pass**: the package becomes eligible for a default-change proposal for `--to claude`, which first needs a
  confirmation round (separate pre-registration and budget). **B Fail**: this is cheap-first's first improvement
  round (section 1, B); one more is allowed, and if it also fails the switch stays off and work on it stops. The docs
  mark it "measured, not recommended" with numbers and a report link.
- **C**: diagnostic; no default changes either way.
- **Unknown**: state why and draw no conclusion.
