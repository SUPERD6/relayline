     - **墙钟**：ccxcheapfirst2 的中位墙钟 / self 的中位墙钟 ≤ 2（第一轮的公式；(i)(ii)）。

## 3. 功效分析和样本量

分析单位是题，每题每臂跑 1 次。A1/A2 的题各自独立写成。**B、C 的题按仓库聚类**（B 每仓库 6 题、至少 10 个仓库；C 每仓库 4 题、至少 6 个）：同一仓库的题难度可能相近，下面的检验假设的独立性比实际多。所以 B、C 还要求按仓库的聚类 bootstrap（第 4 节），B、C 的功效数字也偏乐观：仓库内相关系数 0.2、每仓库 6 题时，有效样本约减半。计算方法：McNemar 用精确枚举；其余用 4 000–20 000 次模拟（标准库脚本，附在 PR 说明里；两次独立审查都重算核对过）。

| 组 | 检验 | 假设的效应 | 水平 | 选定 n 下的功效 | 选定 n |
|---|---|---|---|---|---|
| A1、A2（及 A1x、A2x） | 精确 McNemar，双侧 | p(on 对、off 错) = 0.40，反向 0.05（约为第一轮 codex 16/21 的一半；Claude Haiku 没有第一轮数字，这是假设） | 0.025（Holm 较严的一步） | 0.94 | **48** |

- **B 的花费假设没有直接依据。** 第一轮 G3（几何平均 0.45、标准差 0.61）用的是 Codex 子 agent；换成同厂商子 agent 后，升档档位就是主导自己的模型，升档的题可能比 self 更贵。所以表里也列了几何平均 0.70。开发题实测（第 7 节）和这些假设并列报告。

## 4. 统计

- **配对**：各组都按题。
- **主检验**：A1、A2、A1x、A2x：有效配对上的精确 McNemar（双侧，且要求 b > c）。B、C：配对正确率差的 Tango score 区间单侧 95% 下界；每题对数花费比的配对 t 单侧 95% 上界；总花费比和中位墙钟比（点规则）；每项都在有效配对和全部行两种分析里算。花费恰为 0 的，取对数前换成 $0.0001，并报告这样的个数。
- **按仓库的聚类 bootstrap（B、C）**：有放回地抽仓库（抽中的仓库的所有题一起进；所有新写题出自同一出题者，合为一个聚类 `authored`），10 000 次，随机种子 20261116；在有效配对上算正确率差和每题花费比几何平均的单侧 95% 百分位界（#347）。
- **多重比较**：A1 和 A2 是一个族，Holm 校正，族错误率 α = 0.05；A1x 和 A2x 是第二个族（第一轮的 Codex 结论），Holm 0.05。两个族和它们跑不跑都在开跑前定死，回答的是不同结论（同厂商 / Codex 子 agent），一个族的结果不影响另一个族的判定。**族内某组判 Unknown 时，它的 p 值记为 1**（另一组于是按 0.025 判），族内两组的汇总都出来之前不写该族的判定。B、C 各是一个交并检验（各部分必须都过，内部不需要校正）。B 和 A 回答的是不同设置的不同问题，不合并；C 是诊断。次要指标只做描述，95% 区间不校正并注明；任何次要指标都不能把主判定的 Fail 或 Unknown 变成 Pass。
- **次要指标**（各组适用的都报告，不设门槛）：
  - **主导所属厂商的花费**（本轮主导都是 Claude，即 Claude 自身花费）：每臂单元里所有对主导那家的调用（主导、同厂商子 agent、同厂商审查者）的花费，从账本按厂商汇总（#347），以及每题比的几何平均和 95% 区间。这是用户在主导那家额度上的消耗。B 组两臂几乎全是同一家，所以它接近总花费；C 组里它把主导和 Codex 子 agent 分开。主花费指标仍是总花费。
  - 正确率（带分子分母）、每次成功花费、累计和中位墙钟；每臂撞上限次数（B、C）；升档率、首档与升档花费（B）；sensitivity 回执标为"改动前已通过"的检查占比（B）；Codex 审查者花费（B）；hubmem/hubstart（A2、A2x）；neutral 伤害检查（A1、A1x）；按题目来源和仓库分层（B、C）；仓库数和占比最大的仓库（B、C）；env_clean 子集。
- 零：某臂成功 0 次时没有有限的每次成功花费。

## 5. 中断和重跑

同第一轮，另加第 0 节的无效行规则：

- 脚本不能续跑。被停的组保留所有已完成的行，花费计入总额，判 **Unknown**；不续跑。**跑完的组（Pass 或 Fail）一律不重跑。**
- **谁能停组：** 只有脚本自己的停止规则（最后一个单元之前的预算停止、花费未知或缺派活证据的行超过 3 个、它的环境检查），或操作者因以下列出的原因停：机器上在跑别的评测或 pytest、机器重启或崩溃、CLI 版本变了。不允许其他人工停组。每次停组都把原因和已完成行数写进修改记录，被停那次的行在报告里完整列出。
- 如果是基础设施故障，单独开 PR 修，**只改评测脚本**。需要改 ccx 本身或某臂提示词才能修的，等于改变了被测的东西；这时除非用户事先批准，否则该组不重跑，修改记录写下批准和改动。在新 pin、新 tag / 输出目录上**从头**重跑，重跑前在修改记录写明原因、修复 PR 和新 pin。重跑不改门槛、样本和题目。被停那次的文件保留。
- 如果是机器原因，不改代码从头重跑，规则同上。
- 每组最多重跑两次；之后该组判 Unknown，总会话停下来问用户。
